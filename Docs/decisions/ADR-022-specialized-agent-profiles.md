# ADR-022: 专用 Profile 构建稳定提示词，动态状态与测试能力留在实例侧

## Status
Accepted

## Date
2026-09-21

## Context

`AgentProfile_SO` 已经统一承载 Persona、模型参数、单轮预算、动作超时和事实容量。现在需要面向游戏 NPC 与 Runtime 自动测试提供专用 Profile，并让两类 Profile 各自拼接不可变系统规则。若把 NPC 状态、工具开关、测试步骤和断言全部塞进派生资产，会重新制造多份真值：同一个 NPC 模板的实例状态不同，同一个测试代理也会运行许多不同用例。

现有边界已经明确：实例工具属于 `AgentHost`（ADR-016/018），动态世界状态属于 `IWorldContextProvider`，session 由 `ProfileKey + instanceId` 隔离（ADR-011/014）。当前 `[AgentTool]` / `[AgentAction]` 已提供白名单反射，不需要为测试再开放任意类型和方法调用。

## Decision

1. 保留 `AgentProfile_SO` 为可直接创建的具体类，增加虚方法 `BuildSystemPrompt()`，默认逐字返回 `PersonaPrompt`；仅将 `Validate(out error)` 改为 virtual。
2. 专用 Profile 自己按固定顺序拼接稳定系统提示词。动态事实、好感、世界快照和查询提示仍逐轮注入，保持缓存前缀稳定。
3. `NpcAgentProfile_SO` 增加展示、身份、性格、说话方式、目标价值、知识边界和初始好感。不可变规则要求角色确信自己是世界内人物、只输出纯台词、对系统术语表示世界内的疑惑且不泄露机制。
4. NPC 好感是按 `sessionId` 隔离的实例状态，由成员 `NpcAffinityController` 持有；模型按本轮互动自行判断是否变化以及变化幅度，每轮只能一次调用 `adjust_affinity(-20..20, reason)`，成功后自动持久化。剧情变化走游戏侧 API，不受模型单轮上限约束。
5. `RuntimeTestAgentProfile_SO` 增加跨多轮测试场景的轮数上限、总超时与失败策略；具体测试目标在每次运行时传入。
6. Runtime 测试工具放入只对 Editor/Development Build 开放的独立模块。优先复用 `[AgentTool]` / `[AgentAction]`；批量动态命令只允许显式 `[RuntimeTestCommand]` 白名单，拒绝任意程序集、类型或方法反射。
7. UI 测试优先使用语义元素 ID和游戏内事件；同时提供 Windows 系统鼠标键盘输入，用于验证真实输入链路。系统输入只能发往 runner 预先绑定的游戏进程与窗口，模型不能枚举、换绑或操作其他窗口。
8. 性能采样同时报告窗口、样本数、平均值、P95、P99 与最大值；不可用指标显式标记，不以 0 代替。
9. Runtime 自动测试使用临时 session，不读写玩家存档；测试通过/失败由游戏侧确定性 oracle 判定。
10. 工具开关继续留在 `AgentHost.ToolToggles`，两个派生 Profile 都不增加工具列表。

## Alternatives Considered

### 继续只用基类

- 优点：零新类型。
- 缺点：NPC 展示信息和测试预算散落在不同组件，资产本身不能表达用途。
- 拒绝理由：两类消费方已有稳定且互不相同的数据需求。

### 在基类增加 ProfileKind 与全部字段

- 优点：只有一个资产类型。
- 缺点：字段互斥、Inspector 噪音大、运行时需要分支，基类持续膨胀。
- 拒绝理由：Unity 原生多态已经能解决，不需要类型枚举。

### Runtime 测试 Profile 同时保存所有测试用例

- 优点：一个资产即可启动测试。
- 缺点：代理策略、测试步骤和确定性真值绑定；换模型参数会让测试资产整体变化，多个场景也难以独立维护。
- 拒绝理由：Profile 应描述代理，不应成为测试数据库。

### 以模型自报 PASS/FAIL 作为结果

- 优点：无需游戏侧检查代码。
- 缺点：结果非确定且可幻觉，不能定位真实状态差异。
- 拒绝理由：不满足自动测试的可信性要求。

### 移植旧 Mu 的完整 NPC 性格与关系系统

- 优点：多维性格轴、情绪乘数、关系变化和自主行为看似齐全。
- 缺点：策划难以预测数值结果，动态状态与 Profile 混杂，并重新引入已删除的一整代 NPC 子系统。
- 拒绝理由：当前需求只需要可配置人格和一维好感；自然语言人格 + 有界好感足够。

### 开放任意反射调用

- 优点：模型理论上可以调用任何游戏代码，新增测试不必写 wrapper。
- 缺点：等价于 Development Build 后门；schema 不可控，私有实现易变，IL2CPP 裁剪后不可靠。
- 拒绝理由：现有特性注册和成员工具已覆盖白名单调用，测试命令只需一个受控扩展点。

### 开放任意桌面窗口输入

- 优点：可以把测试范围扩展到启动器和其他桌面程序。
- 缺点：模型可能误操作用户程序，目标边界也无法由游戏测试 runner 保证。
- 拒绝理由：本模块只需要验证指定游戏；系统输入必须锁定 runner 提供的进程 ID 与窗口句柄。

### 给纯文本输出增加 Markdown 字符清洗器

- 优点：能机械删除部分 Markdown 符号。
- 缺点：会误删角色正常标点，无法可靠识别旁白与列表，流式输出还会先把违规 token 发到 UI。
- 拒绝理由：先以专用系统规则和回归测试约束；真实遵循率不足时再引入输出验证，而不是字符替换。

## Consequences

- 正向：提示词职责从散装 Persona 文本变为可测试的派生 Profile 输出，普通 Profile 保持兼容。
- 正向：NPC 人格稳定、关系动态且实例隔离；保存不会依赖模型额外决策。
- 正向：测试代理能操作真实游戏并采集证据，但能力受构建类型、runner 和白名单三层限制。
- 正向：Windows 系统输入覆盖真实鼠标键盘链路，同时不把能力扩大成通用桌面自动化。
- 正向：测试最终结果仍可重复、可由代码验证。
- 负向：NPC UI 需要识别派生类型才能显示名称/头像和处理一次性开场白。
- 负向：好感写入失败必须回滚内存状态，持久化实现不能只做 fire-and-forget。
- 负向：Runtime 测试仍需要一个小型 runner、具体 checkpoint 和首个真实用例后才能闭环。
- 负向：Windows 输入实现需要处理焦点丢失、最小化、客户区坐标换算和取消时释放按键等平台细节。
- 约束：实现派生校验时必须调用基类 `Validate`，不得影子声明基类序列化字段；Release 不得注册测试工具。
